# 决策原语设计与 API 契约草案

本文档定义本项目的核心契约：**类型化问题**与**类型化答案**。
契约层实现在 `src/jev_qwen/schema.py`，是全项目唯一需要提前敲定的部分。

## 1. 总体契约

```
决策请求 = 状态(state) + 问题列表(questions[])
决策响应 = 答案列表(answers[])
```

- **state**：一段非结构化上下文，可以是纯文本，也可以是由文本字段构成的 JSON 对象。
  例如一张工单、一段评论、一份订单、一个 agent 的当前观察。
- **questions**：若干带类型的问题，共享同一 state，并行评估。
- **answers**：与 questions 一一对应，每个答案是**类型化的值 + 概率**，可被软件直接消费。

关键约束：

1. **合法输出空间在调用前定义**。答案只能落在 schema 声明的候选集合内。
2. **不生成解释**。模型不写理由、不写散文、不写任意 JSON。
3. **概率必须校准**。模型说 0.8 把握，长期频率上就该约 80% 正确（校准是训练目标，见 §4）。

## 2. 三种原语的精确语义

### 2.1 Noul —— 是/否判断

| 项 | 内容 |
|---|---|
| 问题字段 | `id`、`prompt`（自然语言命题，如"这张工单是在请求退款吗？"） |
| 答案 | `p_true ∈ [0,1]`：命题为真的概率 |
| 语义注意 | `p_true≈0.5` 表示"是/否各半"的**不确定**，**不是**"程度中等" |
| 典型用途 | 内容标记、条件门控、独立判据 |

阈值由调用方代码决定（如 `p_true > 0.7` 才打标签），模型只给概率，不做决策。

### 2.2 Choice —— N 选 1

| 项 | 内容 |
|---|---|
| 问题字段 | `id`、`prompt`、`options[]`（≥2 个互斥且穷尽的候选） |
| 答案 | `selected`（argmax 选项）、`probabilities{option: p}`（归一化，和为 1）、`confidence` |
| 语义注意 | 正确答案**必须在 options 里**。若真实类别缺失，概率仍被迫落在剩余选项上——这是最大的设计风险 |
| 典型用途 | 工单路由、意图分类、工具/模型选择 |

`confidence` 定义为概率分布的**集中程度**（如 max 概率或归一化熵的补），它**不代表整体流程正确性**。

### 2.3 Score —— 有序等级评分

| 项 | 内容 |
|---|---|
| 问题字段 | `id`、`prompt`、`levels[]`（有序等级标签，如 `["低","中","高","紧急"]`） |
| 答案 | `expected_score`（按等级序号插值的期望分）、`probabilities{level: p}`、`confidence` |
| 语义注意 | 等级是**有序**但**不一定等距**。`expected_score` 是概率加权的序号期望，仅作排序/聚合用 |
| 典型用途 | 优先级排序、风险评级、质量评估 |

## 3. API 契约草案（JSON 形态）

### 请求

```json
{
  "state": {
    "title": "订单一直没发货",
    "body": "下单三天了还在处理中，能退款吗？"
  },
  "questions": [
    {"id": "q1", "type": "noul", "prompt": "该工单在请求退款吗？"},
    {"id": "q2", "type": "choice", "prompt": "应路由到哪个队列？",
     "options": ["物流", "退款", "技术支持", "其他"]},
    {"id": "q3", "type": "score", "prompt": "该工单的紧急程度",
     "levels": ["低", "中", "高", "紧急"]}
  ]
}
```

### 响应

```json
{
  "answers": [
    {"id": "q1", "type": "noul", "p_true": 0.87},
    {"id": "q2", "type": "choice", "selected": "退款",
     "probabilities": {"物流": 0.12, "退款": 0.71, "技术支持": 0.05, "其他": 0.12},
     "confidence": 0.71},
    {"id": "q3", "type": "score", "expected_score": 2.4,
     "probabilities": {"低": 0.05, "中": 0.30, "高": 0.50, "紧急": 0.15},
     "confidence": 0.50}
  ],
  "meta": {"model": "jev-qwen-readout-v0", "latency_ms": 214}
}
```

## 4. 概率读出（零训练路线）设计

Qwen3.5-4B 是自回归生成模型，本项目第一阶段不训练，而是**从候选 token 的似然中读出概率**：

```
state + question + option_i  →  P(option_i | prompt)   对每个候选项
                →  softmax 归一化  →  原语的概率输出
```

要点：

- **Choice**：对每个选项构造一个简短的补全（如选项标签本身），取该补全的对数似然，
  对所有选项做 softmax 归一化，得到 `probabilities`。
- **Noul**：视作 2 选项的 Choice（"是" / "否"），取"是"侧概率为 `p_true`。
- **Score**：对每个等级标签同样做似然读出，归一化得 `probabilities`，
  再按等级序号加权平均得 `expected_score`。
- **归一化**是必须步骤：原始似然不可比（长度偏差），需做长度归一化后再 softmax。

局限（与 Jev 的差距）：

- 原生 LLM 的似然**通常不校准**，需要温度缩放（temperature scaling）或后续微调。
- 读出质量高度依赖 prompt 模板与选项措辞，需做模板敏感性实验。
- 一次前向只能读出一个选项的似然，N 个选项需 N 次前向（或用 batch 并行），
  不是 Jev 那种真正的单次并行输出头。**这是复刻与原版的根本差距**，
  消除它需要改模型结构加决策头（超出零训练范围）。

## 5. 校准评估指标

| 指标 | 含义 |
|---|---|
| **准确率** | argmax 是否命中标签 |
| **ECE**（Expected Calibration Error） | 概率与经验频率的分桶偏差，衡量"说到做到"程度 |
| **MCE**（Maximum Calibration Error） | 最差分桶偏差 |
| **Brier Score** | 概率的均方误差，同时衡量准确与校准 |
| **延迟** | 单次决策的端到端耗时 |

评测脚本 `scripts/evaluate.py` 将输出以上指标，按原语类型分别统计。

## 6. 治理注意

- Jev 式决策若用于招聘、信贷、安全等高影响场景，仍受 EU AI Act / NIST AI RMF 等框架约束。
- 记录模型版本、决策定义版本、策略版本与结果；保留人工申诉通道。
- 模型只**为策略提供信息**，不应**成为策略本身**——阈值、权限、回退、副作用留在代码里。
